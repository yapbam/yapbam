Yapbam delivery process

  1. Get the translations from Crowdin.
    First check on Crowdin that no translation occurred since last build (if so build the project).
    Launch the com.fathzer.localization.crowdin.GetTranslationsCmd from the jlocal-tools (private) project with arguments projectId=46987 token=yourToken lng=fr-FR:fr,pt-BR:pt,de-DE:de,en-US:,zh-TW:zh,tr-TR:tr,nl-NL:nl,ru-RU:ru,ro-RO:ro,pl-PL:pl,hu-HU:hu,es-ES:es,it-IT:it,ar-SA:ar,ja-JP:ja,el-GR:el where=workspaceRoot moved=YapbamWeb:hosting/yapbam/www,YapbamCommons:yapbam-commons
    Be aware that there's a bug in ar language export: The Tip.1 key in Yapbam Resource_ar.properties file is corrupted during this export.
    You'll have to carefully check the differences before committing the changes to Git.
    Be aware that Crowdin sometimes changes the format of the downloaded files, this command may simply fail or return a partial set of languages
    The alternative is then to download the translations manually from Crowdin and place them in the right directories.
    Then, check if YapbamCommons translations have changed. In such a case, update the artifact.
    Check if Yapbam web resources have changed. If so, update them on the yapbam server (see private hosting project).
    Be aware of changes in Yapbam web resources. Due to a Crowdin bug, ':' and '=' characters are preceded by an escape '\' character. Note also that the French and English versions of 'TranslationNeeded.supported' key are not the one stored in Crowdin.
  2. Ensure version number and release notes are correct.

    Set the version number in the pom.xml file.

    Update the release notes in the src/localization/[fr/]relnotes.txt file and ensure the release dates are correct.

  3. Run mvn clean package at the project root folder. This creates a ready to deploy zip file in the project directory.
  4. Create the windows installer with NSIS.

    Select the "Installer based on a zip file" option and enter $EXEDIR\Yapbam as default folder.

  5. Run net.yapbam.deployment.YapbamDeployer in (private) project YapbamDeployment.
    Make sure to set the right versions in the program fields.

    Wait for it to complete (it is long as this class uploads Yapbam to SourceForge).

    Copy the release notes on the official site (the deployer deploys only on SourceForge)

  6. Test everything is fine.

    Test that the autoupdate is ok with a copy of the previous version of yapbam.

    Also test that the archives on SourceForge are ok (sometimes, upload results in a partial file).

    The good news: If something is wrong, you can start again the process from any previous point.

  7. In the SourceForge file browser, give the linux, BSD, etc... attributes (or windows) to the new uploaded files.
  8. Commit pending changes to GitHub repository.

    Then, create a release for the deployed version on GitHub.

  9. Post a comment on Bluesky.
  10. Post replies on opened bug reports or feature requests.

A way to carefully test the auto update before any deployment

  1. In net.yapbam.update.VersionManager#getUpdateURL, change the updateinfo URL to a local file and put a fake version number in net.yapbam.update.version.txt
  2. In this local file, copy the lines output by srcTests/net.yapbam.update.GetHashAndSize
  3. Launch this modified version of yapbam.
  4. Try to update.
    5. Make sure to revert net.yapbam.update.VersionManager#getUpdateURL after testing.
